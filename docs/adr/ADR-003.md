# ADR-003: Real mined bugs over generated challenges

**Status:** Accepted, then superseded by [ADR-008](ADR-008.md)

> **Superseded by [ADR-008](ADR-008.md).** The structural sourcing requirement recorded below (a test-only commit before the fix, with students checking out that first commit) was replaced by platform-fork challenge construction. The broader principle, real mined bugs over generated ones, still holds. This record is kept unchanged as a point-in-time decision; see ADR-008 for the current model.

## Context

The challenge set is the product. The quality and authenticity of the bugs determine whether the app is worth using. Options considered:

- Generate bugs with a language model
- Write synthetic bugs manually, each designed to teach a concept
- Source bugs from real fix commits in open-source .NET repositories

## Decision

Source all bugs from real fix commits in MIT, Apache 2.0, or BSD-licensed .NET repositories. Each bug must meet the following criteria:

- A real failing test in the upstream repo that verifies the fix
- A structural requirement: the pull request must contain a test-only commit before the fix commit. That first commit adds a failing test reproducing the bug without changing any production code. The second commit introduces the fix. Students check out the first commit.
- A symptom description that does not point to the location of the bug
- Three tiered hints (nudge, area, file and line) that are the only place the location appears
- Attribution to the original commit and PR

GPL and copyleft licenses are excluded. AutoMapper was rejected on this basis.

### Difficulty definition

Difficulty reflects how hard the bug is to locate, not how complex the fix is. A one-character fix can be rated Hard if finding it requires reading across multiple abstraction layers or following an indirect call chain. A multi-file fix can be rated Easy if the test failure message points directly at the problem area. Tiered hints are calibrated to the navigation challenge, not the implementation effort.

## Consequences

**Accepted trade-offs:**

Sourcing is manual and slow. Finding a bug that meets both the quality bar (isolated fix, misleading symptom, navigable in three hints) and the structural requirement (test-only commit before the fix) takes substantial research. Most maintainers combine the test and fix in a single commit, which disqualifies the PR. The library grows incrementally.

The test-first commit structure is a binding constraint. Without it, there is no known-failing checkpoint for students to work from and no safe commit to distribute as the challenge starting point. This limits candidate repos to those where at least some external contributors demonstrate the bug with a test before the maintainer applies the fix.

The planned solution to this constraint is a platform-fork model: Skill Issue maintains a fork of each challenge repo and commits the failing test there, decoupled from the upstream PR structure. This removes the sourcing dependency on upstream commit ordering and significantly expands the available challenge library. It is not yet implemented.

License vetting is required for every new repo. This cannot be automated safely.

Not every good bug has a clean failing test. Some fixes are verified by integration or regression tests that are hard to point to precisely.

**Benefits:**

The bugs are real and have passed code review in production codebases. The symptom is what someone would actually encounter.

The test infrastructure already exists in the upstream repo. There is nothing to maintain on the challenge side.

Students interact with real codebases and real test suites, not contrived examples.
