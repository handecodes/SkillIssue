# ADR-006: Fork verification trusts the fork's own CI (self-reported)

**Status:** Accepted (known limitation, with a roadmap if stakes change)

## Context

A challenge is verified by inspecting the student's fork through the GitHub API: the fork must be a fork of the seeded challenge repo, must be owned by the signed-in user, and the latest completed run of the scoped `challenge.yml` workflow on the default branch must have concluded `success`.

The decisive signal — the workflow conclusion — comes from CI that runs **inside the student's own fork**. The student has full write access to everything in that fork: the workflow file (`.github/workflows/challenge.yml`), the test project, and the source under test.

This means a determined student can obtain a `success` conclusion **without actually fixing the bug**, by tampering with the artifact the platform trusts:

- replace `challenge.yml` with a no-op job (e.g. `run: echo ok`) so it concludes green without running the test;
- edit the catching test itself to assert something trivially true;
- otherwise neuter the check while leaving the planted bug in place.

The platform does not (and with self-reported CI, cannot) detect this. It is inherent to verifying via CI that the user controls.

A separate, unrelated hole — submitting *someone else's* already-green fork — was a real authentication gap and **is closed** (the verifier now requires the fork's GitHub numeric owner ID to match the signed-in user; see the ownership check in `GitHubVerificationService.VerifyForkAsync`). This ADR is only about the self-tampering case.

## Decision

Accept self-reported fork CI as the verification mechanism, with the tampering limitation documented and deliberate — **not** an oversight.

The accept rests on the current stakes: a PASS only advances the **submitting user's own** progress page (`uniqueSolved`, per-repo counts in `GetProgressSummaryAsync`, scoped to their `UserId`). There are no grades, no leaderboard, no certificates, nothing another user can see or that ranks users against each other. So the only thing a tamperer gains is a falsified view of **their own** progress — gaming the verifier is cheating yourself. At this stake level, the simplicity of self-reported CI (no infrastructure to run untrusted code) outweighs the integrity gap.

## Consequences

**Accepted trade-offs:**

A student who wants to can mark a challenge solved without solving it, by editing their own `challenge.yml` or test. This is accepted because the only victim is their own progress tracking.

The verifier's PASS is therefore an *honesty-assisted* signal, not a tamper-proof proof of correctness. Any future feature that raises the stakes invalidates this trade-off (see roadmap).

**Benefits:**

No platform-side execution of untrusted student code — which would be the only fully tamper-proof design, and which carries its own substantial threat model (sandboxing, resource limits, network isolation, supply-chain exposure from arbitrary fork contents). Avoiding it keeps the platform simple and safe to operate.

**Roadmap — revisit if stakes are ever added (grades, a leaderboard, certificates, anything cross-user or credentialing):**

1. **Tamper-proof:** platform-side sandboxed execution — clone the fork at the run's head SHA and run the scoped test in our own isolated CI/sandbox, ignoring the fork's self-reported conclusion. This is an architectural change with its own threat model (running untrusted code) and would warrant its own ADR.
2. **Lighter mitigation (raises the bar without full execution):** pin the workflow — fetch `.github/workflows/challenge.yml` at the run's head SHA and reject if its hash differs from the seeded original — **plus** diff the head commit against the seeded base to reject changes that touch the test file or workflow. This blocks the neuter-the-workflow and edit-the-test paths short of full sandboxing.

Until stakes change, neither is implemented; this decision stands.
