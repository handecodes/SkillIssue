# ADR-001: Blazor Server over Razor Pages or SPA

**Status:** Accepted

## Context

The challenge detail page needs interactivity: revealing hints one at a time, submitting a fork URL, and displaying a verification result without a full page reload. The options considered were:

- Razor Pages with JavaScript for the interactive parts
- A React or Vue SPA backed by a .NET API
- Blazor Server (interactive SSR over SignalR)
- Blazor WebAssembly

The project is written by a single developer who works primarily in C# and wanted to avoid the JS ecosystem.

## Decision

Use Blazor Server for all interactive components. The app runs as a single .NET process. No separate API. No JavaScript framework.

## Consequences

**Accepted trade-offs:**

Each connected user holds a SignalR circuit on the server. This ties memory and a thread to every active session. The app does not scale well to large numbers of concurrent users on a small host.

HTTP middleware does not intercept Blazor circuit events. Button click handlers run over the SignalR channel, not HTTP. Rate limiting for the fork submission endpoint had to be implemented as a singleton service injected into the component, not as middleware. See `ForkSubmissionLimiter.cs`.

If the server restarts, all active sessions lose their circuit state and see a reconnect prompt.

Cold starts are noticeable. Blazor Server requires a warm process to respond quickly.

**Benefits:**

C# throughout. No context switch between front end and back end. No TypeScript, no npm, no build step for the UI.

Server-side rendering is the default. First-load performance is good without extra configuration.

No API layer. Components call services directly through constructor injection.
