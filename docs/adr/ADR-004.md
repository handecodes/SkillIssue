# ADR-004: Users work in their own IDE

**Status:** Accepted

## Context

To fix a bug, users need to read and edit code. The options considered were:

- Build an in-app code editor (Monaco, CodeMirror) backed by a server-side execution environment
- Link to a web-based IDE or sandbox (Gitpod, GitHub Codespaces)
- Require users to fork the repo and work locally in their own environment

## Decision

Require users to fork the challenge repo and work locally. The app provides the brief, error output, and hints. Verification is done by checking CI on the user's fork via the GitHub API.

## Consequences

**Accepted trade-offs:**

Higher onboarding friction. Users must have Git, the relevant SDK, and a GitHub account configured locally. Users who hit setup problems get no help from the app.

Verification depends on the upstream repo having a working CI workflow. If the fork's CI is absent, misconfigured, or slow, verification fails or takes a long time.

There is no feedback on approach, only pass or fail.

**Benefits:**

No editor infrastructure to build or maintain. No sandboxed code execution, no resource limits, no security surface around running arbitrary user code.

Users practice in the tools they will use on the job: their own IDE, their own terminal, their own Git workflow.

The full IDE experience is available: debugger, search across files, refactoring tools, language server diagnostics. A web editor would be a step down from this.

The fork-and-push workflow is standard open-source practice. Students are practicing that as well.
