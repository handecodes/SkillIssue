# ADR-002: SQLite with a path to SQL Server migration

**Status:** Accepted

## Context

The app needs a relational database for users, challenges, attempts, and hints. Options considered:

- SQLite (file-based, zero setup)
- SQL Server (production-grade, Azure-native)
- PostgreSQL

The priority at this stage was simplicity: no connection strings to manage locally, no database server to run, easy to reset during development.

## Decision

Use SQLite via EF Core. Keep the data layer provider-agnostic so a SQL Server migration requires only a connection string and provider swap, with no model changes.

In practice: no SQLite-specific query hints, no raw SQL with SQLite syntax, no SQLite-only EF features.

## Consequences

**Accepted trade-offs:**

SQLite allows only one writer at a time. Under concurrent write load (multiple users submitting forks simultaneously), writes will queue. Acceptable at current scale, not acceptable long-term.

The SQLite file lives at `/data/skillissue.db` in the container. The current Azure App Service deployment does not mount a persistent volume, so the database resets on container restart. This is a known limitation of the deploy configuration, not of SQLite itself.

No connection pooling in the same sense as a client/server database.

**Benefits:**

Zero local setup. Clone, set user-secrets, run.

EF Core abstracts the provider. Switching to SQL Server or PostgreSQL later requires a one-line change to `Program.cs` and a new migration add.
