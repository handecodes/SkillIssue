# ADR-008: Platform-fork challenge construction

**Status:** Accepted (supersedes the sourcing and verification model of [ADR-003](ADR-003.md))

## Context

[ADR-003](ADR-003.md) committed the project to real mined bugs and bound challenge construction to a structural requirement: the upstream pull request had to contain a test-only commit before the fix commit, and students checked out that first commit as the starting state. That requirement turned out to be the limiting factor on the whole library.

The deeper problem is structural, not just scarcity. A challenge is only valid if the codebase is genuinely failing at the student's starting state. Sourcing that state from upstream history almost never works, because maintainers add the catching test in the same commit as the fix. The parent commit is therefore green: it predates the test, so nothing catches the bug. The narrow set of PRs where an external contributor first pushes a failing test, and the maintainer fixes it in a later commit, is small and slow to find, and most candidate repos never produce one.

The check-out-a-specific-SHA workflow was also awkward for students: it asks them to detach to a commit and work from there, which is not how anyone fixes a bug in practice.

## Decision

Construct each challenge as a platform-maintained fork, not as a pointer into upstream history.

For each challenge:

- Fork the upstream repo to `handecodes/skillissue-<name>` and enable Actions on the fork.
- On the fork's default branch, reintroduce the bug as a small, localized, single-file source change. The catching test already exists at the fork's current main, so the default branch is genuinely red.
- Add a scoped, pinned `.github/workflows/challenge.yml` that runs only the target test (SDK pinned via `global-json-file`, target framework and coverage settings constrained per the repo's needs).

The seeded `GitHubUrl` for the challenge is the platform fork, not the upstream library.

Verification (`GitHubVerificationService.VerifyForkAsync`) passes when all of the following hold:

- the submitted fork's parent equals the seeded `GitHubUrl`;
- the fork's numeric owner ID matches the signed-in user (the ownership binding from [ADR-006](ADR-006.md));
- the latest completed run of the scoped `challenge.yml` workflow, on the fork's default branch, concluded `success`.

The scoping to `challenge.yml` on the default branch is load-bearing: a fork inherits the upstream's own workflows, and a repo-wide latest-run query would read the wrong workflow and both falsely pass and falsely fail. The named failing test remains display-only.

The student workflow is: fork the platform fork, enable Actions on the fork, fix the bug on the default branch, push, and the scoped CI run is checked automatically. There is no `git checkout <sha>`.

This supersedes ADR-003's structural sourcing requirement (test-only commit before the fix) and its check-out-the-first-commit starting state. ADR-003's broader principle, real mined bugs over generated or synthetic ones, still holds; what is superseded is how the failing starting state is constructed and how a fix is verified.

## Consequences

**Accepted trade-offs:**

The platform now maintains a fork per challenge. Each fork must keep Actions enabled and keep its `challenge.yml` pinned and working. Upstream toolchain drift (SDK pins, preview-SDK `global.json`, multi-target frameworks, coverage gates) has to be absorbed in the fork's `challenge.yml` rather than relying on the upstream's own CI.

Verification still trusts CI that runs inside the student's own fork. A student can tamper with their own `challenge.yml` or test to self-report a pass. This is the accepted, documented limitation of [ADR-006](ADR-006.md), unchanged by this decision: stakes are the user's own progress, so gaming the verifier is cheating yourself.

Because the seeded URL is now a fork, the seeder content is the source of truth for which fork each challenge points at, and a content change still triggers a destructive reseed under the current ephemeral database (see [ADR-007](ADR-007.md)).

**Benefits:**

Every challenge has a guaranteed-red starting state by construction, instead of depending on an upstream commit happening to be red. The library is no longer gated on upstream commit ordering, which is what let it grow to ten challenges across ten distinct domains.

The student works the way they would on the job and in open source: fork, fix on the default branch, push, let CI confirm. No detached checkout, no SHA to copy.

Verification is uniform across every challenge. `challenge.yml` is the single workflow path the verifier scopes to, regardless of how the upstream repo structures its own CI.
