# ADR-007: Seeding must be idempotent and non-destructive before persistence is added

**Status:** Accepted (a blocking constraint on the ADR-002 persistence migration)

## Context

Challenge content lives in the seeder (`DbSeeder.SeedAsync`), which runs on every application startup (after `MigrateAsync`). The seeder is the source of truth for production content (per [ADR-002](ADR-002.md), there is no persistent volume, so every deploy resets SQLite and reseeds from the image).

The reseed is **destructive**: it deletes the entire challenge set *and* all user `Attempts` (in FK order: `Attempts`, `HintTiers`, `FailingTests`, `Bugs`, `Repos`), then re-inserts the challenges fresh. It wipes `Attempts` because it delete-and-re-inserts `Bugs` with new auto-generated IDs, which would orphan the `Attempt.BugId` foreign keys otherwise.

An idempotency guard is supposed to make a second run safe by skipping the reseed when the database already holds the current challenge set. That guard was originally keyed off a single hard-coded repo URL (`JamesNK/Newtonsoft.Json`). When challenge #4 was rebuilt onto a platform fork, that row's `GitHubUrl` changed and the marker silently stopped matching any seeded row — so the guard never fired and the destructive reseed ran on **every** startup. This was fixed (set-based guard keyed off the whole expected set of repo URLs, so a single URL change can't disable it; an unchanged already-seeded DB now correctly skips).

That fix stops the *spurious* reseed-on-every-boot. It does **not** make seeding non-destructive when the challenge set genuinely **changes**: adding, removing, or editing a challenge changes the expected set, the guard correctly detects the difference, and the reseed runs — still deleting all `Attempts`.

Today this is harmless: with no persistent volume the database is ephemeral, so there is no user progress to lose (it resets every deploy regardless — the known ADR-002 limitation). The danger is latent.

## Decision

**Before any persistent volume is added (the ADR-002 path to preserving user data), seeding must be made idempotent and non-destructive. Until then, adding persistence is BLOCKED.**

Concretely, the future seeding redesign must:

- **Upsert** challenges by a stable natural key (e.g. `Repo.GitHubUrl` + bug FQN/title), inserting missing rows and updating changed ones — never bulk-`DELETE` + re-insert.
- Keep `Bug` IDs **stable** across reseeds so existing `Attempt.BugId` references stay valid.
- **Never `DELETE FROM Attempts`.** User progress must survive a content update.

## Consequences

**Accepted trade-offs / the explicit dependency:**

This records a hard ordering constraint: the persistence migration (mounting a volume so `Attempts` survive restarts) **cannot proceed** until non-destructive seeding lands. If a volume were added with the current seeder, the first deploy that changes the challenge set would erase every user's solved-challenge history — silently, on startup.

The interim set-based guard is a *mitigation, not the fix*: it prevents the wipe only while the challenge set is unchanged. A content change still triggers a destructive reseed. That is acceptable only because the database is currently ephemeral.

**Benefits:**

Until persistence is needed, the seeder stays simple (delete-and-reseed from the image is trivially correct on an empty database), and the constraint is captured here so a future migration can't skip it. Cross-references [ADR-002](ADR-002.md) (no persistent volume / reseed-from-image).
